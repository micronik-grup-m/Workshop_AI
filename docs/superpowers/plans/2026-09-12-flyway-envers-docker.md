# Flyway + Envers + Docker Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **No git repository in this project.** Every task's final step would
> normally be a commit; instead it says "mark task done (no git repo)".

**Goal:** Replace Hibernate's auto-DDL with Flyway-managed migrations, add Hibernate Envers audit history on `Employee`/`AppUser`, and add a Docker Compose stack (PostgreSQL + the containerized app) so the whole backend can be tested against a real database.

**Architecture:** Flyway becomes the single source of truth for schema (`ddl-auto: validate`), with portable SQL migrations that run unchanged on H2 (local dev) and PostgreSQL (Docker). `Employee` and `AppUser` gain `@Audited`, producing `_aud` shadow tables plus a shared `revinfo` table. A new `docker` Spring profile switches the datasource to PostgreSQL and binds the server to `0.0.0.0` (required for Docker port-mapping to reach the container) — the default profile keeps H2 + `127.0.0.1` exactly as today.

**Tech Stack:** Spring Boot 4.1.1's `spring-boot-starter-flyway` (NOT raw `flyway-core` — see Global Constraints), `flyway-database-postgresql`, Hibernate Envers (`hibernate-envers`, version-aligned with `hibernate-core` automatically), PostgreSQL JDBC driver, Docker + Docker Compose.

**Spec:** `docs/superpowers/specs/2026-09-12-flyway-envers-docker-design.md`

## Global Constraints

- **Use `org.springframework.boot:spring-boot-starter-flyway`, not `org.flywaydb:flyway-core` directly.** Verified fact: Spring Boot 4 split Flyway's auto-configuration into its own module (`spring-boot-flyway`), which is NOT pulled in by `flyway-core` alone — adding only `flyway-core` compiles fine but Flyway silently never runs (no error, just 0 migrations applied), which then makes Hibernate's `ddl-auto: validate` fail with "missing table" once the real migrations are added. Confirmed via a live test run: with only `flyway-core` present, Flyway never logged anything and Hibernate validation failed; switching to `spring-boot-starter-flyway` fixed it immediately (Flyway logged "Migrating schema... Successfully applied 3 migrations").
- Also add `org.flywaydb:flyway-database-postgresql` (Flyway's own PostgreSQL support module — also split out separately) and `org.postgresql:postgresql` (runtime scope).
- No explicit versions on any of these four dependencies — Spring Boot 4.1.1's parent BOM manages them (verified resolved versions: `spring-boot-starter-flyway` 4.1.1 → `flyway-core` 12.4.0; `flyway-database-postgresql` 12.4.0; `hibernate-envers` 7.4.5.Final, matching the project's existing `hibernate-core`; `postgresql` 42.7.13).
- Migration SQL must be portable across H2 and PostgreSQL: `BIGINT`/`INTEGER GENERATED BY DEFAULT AS IDENTITY` (SQL:2003 identity columns, supported by both), `VARCHAR(n)`, `NUMERIC(38,2)`, `DATE`, `SMALLINT` (not H2's non-portable `TINYINT` or native `ENUM` type — both verified to work fine with Hibernate's schema validator).
- **Envers tests must NOT use `@Transactional`.** Verified fact: Envers only persists audit rows for transactions that actually commit — a Spring test's `@Transactional` rolls back at the end, so `AuditReader.getRevisions(...)` returns an empty list even though the code path is otherwise correct (confirmed by reproducing this exact failure). Use a plain `@SpringBootTest` with manual `@AfterEach` cleanup instead (`repository.deleteById(...)`).
- **Read audit history through an `EntityManager` created from `EntityManagerFactory.createEntityManager()`, not the `@Autowired EntityManager` proxy.** Verified fact: outside an active Spring-managed transaction, the injected `EntityManager` proxy is closed and throws `IllegalStateException: The associated entity manager is closed!` on use. Create one directly from `EntityManagerFactory` and close it in a `finally` block.
- Docker base images (verified to exist via the Docker Hub registry API): `maven:3.9-eclipse-temurin-21` (build stage), `eclipse-temurin:21-jre-alpine` (runtime stage), `postgres:16-alpine` (database service).
- The `docker` Spring profile MUST set `server.address: 0.0.0.0` — the default profile's `server.address: 127.0.0.1` (an intentional security decision from the original spec) would make the containerized app unreachable through Docker's port mapping.
- No git repository — commit steps are replaced with "mark task done (no git repo)".

```java
// src/test/java/ro/micronikgrupm/mcp/client/employee/EmployeeAuditTest.java
package ro.micronikgrupm.mcp.client.employee;

import jakarta.persistence.EntityManager;
import jakarta.persistence.EntityManagerFactory;
import org.hibernate.envers.AuditReader;
import org.hibernate.envers.AuditReaderFactory;
import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;

import java.math.BigDecimal;
import java.time.LocalDate;
import java.util.List;

import static org.assertj.core.api.Assertions.assertThat;

@SpringBootTest
class EmployeeAuditTest {

    @Autowired
    private EmployeeRepository repository;

    @Autowired
    private EntityManagerFactory entityManagerFactory;

    private Long createdId;

    @AfterEach
    void cleanUp() {
        if (createdId != null) {
            repository.deleteById(createdId);
        }
    }

    @Test
    void recordsARevisionOnEachChange() {
        Employee employee = new Employee();
        employee.setFirstName("Maria");
        employee.setLastName("Ionescu");
        employee.setEmail("maria.ionescu@example.com");
        employee.setDepartment("Marketing");
        employee.setSalary(new BigDecimal("6000"));
        employee.setHireDate(LocalDate.of(2024, 1, 15));
        employee = repository.saveAndFlush(employee);
        createdId = employee.getId();

        employee.setSalary(new BigDecimal("7000"));
        repository.saveAndFlush(employee);

        EntityManager entityManager = entityManagerFactory.createEntityManager();
        try {
            AuditReader auditReader = AuditReaderFactory.get(entityManager);
            List<Number> revisions = auditReader.getRevisions(Employee.class, employee.getId());

            assertThat(revisions).hasSize(2);

            Employee firstRevision = auditReader.find(Employee.class, employee.getId(), revisions.get(0));
            Employee secondRevision = auditReader.find(Employee.class, employee.getId(), revisions.get(1));

            assertThat(firstRevision.getSalary()).isEqualByComparingTo("6000");
            assertThat(secondRevision.getSalary()).isEqualByComparingTo("7000");
        } finally {
            entityManager.close();
        }
    }
}
```

**Important:** do NOT add `@Transactional` to this test class — see Global Constraints. If you add it, the test will compile and run but fail with "Expected size: 2 but was: 0" because Envers only records committed changes, and Spring's test-managed transaction rolls back at the end.

CREATE TABLE revinfo (
    rev INTEGER GENERATED BY DEFAULT AS IDENTITY,
    revtstmp BIGINT,
    PRIMARY KEY (rev)
);

CREATE TABLE employee_aud (
    id BIGINT NOT NULL,
    rev INTEGER NOT NULL,
    revtype SMALLINT,
    first_name VARCHAR(255),
    last_name VARCHAR(255),
    email VARCHAR(255),
    department VARCHAR(255),
    salary NUMERIC(38,2),
    hire_date DATE,
    PRIMARY KEY (rev, id),

CREATE TABLE app_user_aud (
    id BIGINT NOT NULL,
    rev INTEGER NOT NULL,
    revtype SMALLINT,
    username VARCHAR(255),
    password_hash VARCHAR(255),

    CONSTRAINT fk_app_user_aud_revinfo FOREIGN KEY (rev) REFERENCES revinfo (rev)
